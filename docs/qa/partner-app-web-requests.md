## الفكرة باختصار

هنعمل تطبيق Flutter منفصل لصاحب المغسلة، فيه كل اللي بيقدر يعمله من لوحة المغسلة.

**التطبيق هيستخدم نفس API اللوحة `/api/v1/vendor/*`** ومش هيكلم Supabase مباشرة. كده قواعد الصلاحيات والخصومات والتدقيق تفضل عندك في مكان واحد.

من مراجعة اللوحة شفنا طلبات القراءة بس، ومحتاجين نتأكد من الباقي:

```text
auth/me, auth/refresh, live, setup, notifications, orders, staff, shifts,
schedule, services, offers, reviews, reports, finance, branches
```

ولوحة الأدمن هتفضل ويب، ومفيش مطلوب فيها للتطبيق ده.

**الأولوية:** 🔴 لازم قبل ما نبدأ · 🟠 لازم قبل أول نسخة تجريبية · 🟡 أسئلة وتنظيم

## 🔴 لازم قبل ما نبدأ

### 1. توثيق الـ API

محتاجين OpenAPI/Swagger، أو ملف Postman، أو أي توثيق يغطي **كل** عمليات `vendor`. لكل عملية:

- الـ method والمسار.
- الـ parameters والـ body، وأي حقول مطلوبة.
- شكل الرد، مع مثال حقيقي.
- أكواد الأخطاء وشكل رسالة الخطأ.
- الصلاحية المطلوبة.

القائمة الكاملة للعمليات المطلوبة في آخر الملف.

### 2. الدخول من الموبايل

- إيه عملية الدخول بالظبط، وبتاخد إيه؟
- هل التوكنات تشتغل عادي من تطبيق موبايل، من غير cookies أو أي قيود خاصة بالمتصفح؟
- مدة صلاحية الـ access token والـ refresh token قد إيه؟
- لو طلبين عملوا refresh في نفس الوقت، إيه اللي بيحصل؟ وهل التوكن القديم بيتلغي؟
- إيه عملية تسجيل الخروج، وهل بتلغي التوكن من السيرفر؟
- إزاي المالك يغيّر الباسورد أو يسترجعها؟
- لو المغسلة اتوقفت أو الموظف اتعطل، السيرفر بيرجع إيه؟
- هل فيه rate limit على الدخول أو باقي العمليات؟

### 3. تسجيل جهاز الموبايل للإشعارات

جدول `push_devices` بيقبل `app = 'partner'` و`platform = 'ios' | 'android'`. محتاجين:

- عملية لتسجيل التوكن بعد الدخول، وعملية لحذفه عند الخروج.
- تأكيد إنها تحدّث الجهاز لو نفس التوكن كان متسجل قبل كده. الجدول عليه `UNIQUE (token)`، وعليه trigger اسمه `trg_push_devices_take_over_token` بينقل التوكن للمستخدم الجديد.

### 4. وصول إشعارات المغسلة للموبايل

حاليًا `notify_wash` بتكتب في `vendor_notifications` وتنادي `panel_push_vendor_url` عندك. محتاجين تأكيد إن الإرسال:

- بيروح لأجهزة iOS وAndroid كمان، مش الويب بس.
- بيبعت `notification` مع `data`، عشان الإشعار يظهر والتطبيق مقفول.
- بيضيف `href` في `data`، عشان الضغط على الإشعار يفتح الشاشة الصح.
- بيمسح التوكنات المنتهية.
- بيحدد مين يستلم الإشعار: المالك، أو مدير الفرع، أو موظف معين.

ملحوظة: `notify_wash` بتحط نفس النص في `ar` و`en`، فالإشعار مش بيتبعت بلغة المستخدم فعليًا.

### 5. إصلاح المشاكل اللي هتظهر في التطبيق

الأرقام من `dashboards-issues.md`. الإصلاح لازم يكون في الـ API، مش في واجهة الويب بس.

| المشكلة | المطلوب للتطبيق |
|---|---|
| #1 الخصم بيمسح العلامة العشرية ويقبل السالب | الـ API يقبل الكسور الصحيحة ويرفض السالب |
| #2 المالك مش قادر يبدأ الخدمة لو مفيش موظفين | المالك ومدير الفرع يتاخدوا كمسؤولين، أو البدء يتم من غير موظف |
| #3 المواعيد بتعرض أوقات فاتت وأوقات بعد القفل | الـ API يرجّع مواعيد صح، والأفضل من `get_branch_slots`. لسه ظاهرة في صفحة الجدول يوم 1 نوفمبر |
| #6 الحجز الهاتفي بيربط عربية قديمة بلوحة جديدة | يربط بعربية لوحتها مطابقة أو ينشئ عربية جديدة |

### 6. بيئة تجربة

- هل فيه staging؟ لو مفيش، نحتاج مغسلة تجريبية منفصلة تمامًا عن المغاسل الحقيقية.
- حساب مالك، وحساب مدير فرع، وحساب موظف، على فرعين على الأقل.
- ابعت بيانات الدخول بطريقة آمنة، مش في ملف أو شات عادي.

## 🟠 لازم قبل أول نسخة تجريبية

### 7. حالات الطلب والدفع

الطلب والحالات لازم يبانوا صح في شاشة موبايل صغيرة، فمحتاجين:

- جدول الانتقالات المسموحة بين: `pending`, `confirmed`, `waiting`, `in_service`, `completed`, `cancelled`, `no_show`.
- هل الـ API بيرجّع الإجراءات المتاحة لكل طلب؟ ده يخلي الأزرار تتبع القواعد بدل ما نكررها في التطبيق.
- إصلاح #7 (معاملة معلقة لطلب ما اتنفذش) و#8 (الملغي «بانتظار الدفع») و#10 (طلبات «تم الوصول» المفتوحة للأبد).

### 8. الصلاحيات

الحساب بيرجّع `role` و`permissions` و`maxDiscountPct` و`canEditServices`. محتاجين تأكيد:

- إن السيرفر بيتحقق من الصلاحية في كل عملية، مش الواجهة بس.
- قايمة الصلاحيات الكاملة: هل هي دي بس؟ `cancelOrder`, `closeShift`, `collectPayment`, `confirmBooking`, `editServices`, `manageStaff`, `refund`, `runService`.
- هل المالك ليه حد أقصى للخصم؟
- إيه اللي بيرجع لو حساب مالهوش صلاحية طلب عملية؟

### 9. قواعد ثابتة للـ API

- **الأرقام:** الفلوس بالجنيه بكسور ولا بأصغر وحدة؟
- **الوقت:** كل الأوقات UTC ولا بتوقيت القاهرة؟
- **النصوص:** أي حقول بترجع `{ar, en}`، وهل الأخطاء بترجع باللغتين؟
- **الصفحات:** شكل `page` و`per_page` والعدد الإجمالي موحد في كل القوائم؟
- **التدقيق:** الحفظ في اللوحة بيطلب سبب. أي عمليات لازم نبعت معاها `reason`؟
- **الصور:** إزاي نرفع صور الفروع والخدمات من الموبايل؟
- **CSV:** لو عملية التصدير بتبني الملف في المتصفح، نحتاج عملية من السيرفر.

### 10. التحديث الدوري

صفحات اللوحة بتطلب `live` بشكل متكرر. التطبيق هيعمل نفس الحاجة وهو مفتوح، ويعتمد على الإشعارات وهو مقفول.

- إيه أقل فترة مناسبة بين الطلبات؟
- هل حدود Vercel تستحمل الطلبات دي مع زيادة المغاسل؟

### 11. الاسم

الـ API لو بيرجّع نصوص فيها «كارزن» أو Carzen، لازم تتغير لـ Wash Up قبل ما تظهر في التطبيق (مشكلة #11).

## 🟡 أسئلة وتنظيم

1. **تطبيق الموظف:** صفحة التشغيل المباشر بتقول «نفس قواعد تطبيق الموظف»، و`push_devices` بيقبل `employee`، و`staff.pin_hash` موجود. هل فيه تطبيق موظف أو خطة ليه؟ ومين بيسجل فتح وقفل الوردية والنقدي الفعلي حاليًا؟
2. **التغييرات في الـ API:** التطبيق مش بيتحدث عند كل المستخدمين فورًا. أي تغيير يكسر `/api/v1` يبقى في `/v2`، أو تبلغنا قبلها بوقت كافي.
3. **تعريفات قاعدة البيانات:** جداول زي `staff` و`payments` و`transactions` مش موجودة في migrations عندنا. هي عندك؟ ينفع نتفق على مصدر واحد للـ migrations؟
4. **الجداول القديمة:** فيه 12 جدول `legacy_*` على production. لسه محتاجينها؟
5. **طلبات الانضمام:** المغسلة الجديدة بتقدّم منين؟ وهل نضيف التقديم في التطبيق بعدين؟
